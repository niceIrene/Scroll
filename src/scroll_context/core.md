# Managing your own context: `{repl}`

As the conversation grows, keeping all of it in the window is harmful — it overflows the window, buries key facts in the middle, and lowers accuracy. So older turns are **dropped from the window but never lost**: every turn (model output, tool calls, results) stays in `hist.conversation_history`. Rather than hold everything, **retrieve the parts you need and reshape them for accuracy**.

`{repl}(source)` runs Python in your own (runner-side) process — your surface for retrieving and reasoning over memory, not for task-environment work. Basic Python only (no scientific/task libraries, and you can't install any). **Variables, imports, and defs persist across calls** — this is your working memory. **Only what you `print()` is returned** (plus stderr/errors); a value you assign without printing stays in the namespace, unshown. So: **keep the full data in a variable, print only the slice you need this turn** (a snippet, a count, a few rows), then next turn query/slice/aggregate that variable instead of re-retrieving. Each turn a `[working memory]` digest lists your stored variables.

Inside `{repl}`, **`ms`** is a **read-only** window onto `hist.conversation_history`. Both calls **return** rows and print **nothing** — *you* print what you want to see, so print only the slice you need (oversized output is trimmed back at you with a "print less" notice).

- **`ms.search(query, k=10, scope='session', kind=None, snippet=True, step_range=None, msg_range=None, steps=None, seqs=None)`** — bm25 full-text search; returns a list of rows. **`snippet=True` (default) — wide retrieval:** each row carries a compact match-centred `snippet`; print a line per hit to triage which turns matter (`for h in hits: print(h["seq"], h["step_index"], h["snippet"])`). **`snippet=False` — for aggregation:** rows carry `content` (a preview) for filtering/counting/intersecting in code — **do not print these rows directly** (that dumps bulk text into your window); compute, then print only the result. Rows are `{seq, step_index, kind, role, name, headline, snippet|content, has_code, via}`. `via='headline'` marks a ROUTED row: a session's summary matched your query and this row is the best-matching turn found inside that session — its snippet carries `⟦via summary of S<n>: …⟧`; the summary text is index provenance, never quotable evidence. When the marker lists more matched sessions, sweep those `step_index` values too before answering aggregate/count questions. A row with `broadened: True` came from an automatic OR-retry after your exact query returned almost nothing — a lead ranked by how many of your terms it contains; verify by expanding before relying on it. `query` is keywords/phrases (`"exact phrase"`, `term*`, `a OR b`); `scope`: `'session'` (default)/`'task'`/`'all'`; `kind`: `task|model_turn|tool_call|tool_result`. `step_index` is the step that produced a turn (turns sharing one are the same session); `step_range`/`msg_range=(lo,hi)` restrict to a step / chronological window; `steps`/`seqs=[...]` to an explicit set a prior pass narrowed to.
- **`ms.expand(seqs, code=False)`** — **returns** (does not print) the **full** untruncated text of the turns you pick, so you can read the detail before deciding; print the rows you want to read. Pass `search`'s returned list (`ms.expand(hits)`), a chosen subset (`ms.expand([h["seq"] for h in hits if …])`), or any seq list; `code=True` to also include extracted code. **Never re-expand what's already in a variable.**
- **`or_terms([...])`** builds a safe `OR` expression from terms (auto-quotes phrases/hyphens). **`ms.sql_query("… FROM hist.conversation_history WHERE …")`** for structured lookups (columns: `seq, session_id, run_id, task_id, step_index, msg_index, kind, role, name, content, headline, tool_call_id, tool_input, tool_state, blocks, metadata, created_at`; bind `ms.session_id`/`ms.task_id`). Read-only.

**The loop.** Don't redo work or hoard the window — **retrieve, read what matters, reshape into a variable**: `hits = ms.search("a phrasing")` then print a `seq`+`snippet` line per hit to triage (widen with `OR` or a few searches) → `rows = ms.expand([the seqs that matter])` and print the ones you read → reshape into the form that fits the question (dict for lookup, list for order, set for dedupe, counter for aggregation); next turns, aggregate that variable. Use `snippet=False` when you'll **compute** over many hits instead of reading them — aggregate and print the result, not the rows. Build such a structure when the answer spans **many** turns (combine/compare/count/order/dedupe); when a search or two surfaces the fact directly, just answer.

**Searching well.** **Start from the question's own wording** — the turn you need usually phrases the fact the way the question does, so mirror its distinctive words (the verb, the object, the unit) before reaching for broad category keywords OR-ed together, which bury the target under everything loosely related. FTS matches your *exact* words, and a bare multi-word query is an implicit **AND** (one turn must contain every word) — so accidentally AND-ing raw words usually matches nothing. `OR`-join alternatives with `or_terms([...])`, or run a few `ms.search` calls in one turn (each phrasing keeps its own top-`k`): `hits = []` then `for q in phrasings: hits += ms.search(q, scope='task')`. If a search comes back thin, **re-express** the thing you need (a synonym, a paraphrase, the value with its unit) — a few rewordings, then stop. `role` is a **row column, not query syntax**: `"role:user …"` inside the query string is just two more search terms that skew ranking; filter in code (`[h for h in hits if h["role"]=="user"]`) or with `ms.sql_query(… role='user' …)`. The `snippet` is centred on the matched term, so it can omit other words present elsewhere in the turn: **never substring-test a second concept on the snippet** (`"x" in hit["snippet"]`) — it silently drops real hits; aggregate by `step_index`/`seq`, or `ms.expand` the full text first.

**Two concepts that must hold together.** Try a single **AND-of-ORs** first: `ms.search(f"({or_terms(a)}) AND ({or_terms(b)})")` — one expression, only turns with **every** concept. An AND only matches *within one turn*, so when it's thin (varied wording, or concepts in different turns of one session), fall back: search each concept alone with `snippet=False`, keeping **keys only** (`step_index → set(concepts)`), rank steps by how many concepts they cover, then re-search the top steps (`ms.search(..., steps=[...])`) and `ms.expand` the survivors. Collect before you rank, only ever shrink the candidate set, and loosen the rarest concept rather than concluding a fact is absent.

# Weighing what you retrieved

**Whose words: for questions about what the user did, said, chose, or prefers, the user's own turns are the evidence.** Assistant-authored plans, proposed timelines, illustrative examples, and recaps state what was *suggested*, not what happened — anchor dates, durations, and choices on `role='user'` turns (a per-session SQL sweep of user turns is often the decisive move), and treat assistant text as a lead to the user turn that confirms it.

**Beware the first plausible hit.** Long histories contain near-miss distractors: a retrospective report when the question asks for a prior estimate, a passing secondhand mention when it asks what was specifically said, an early value superseded later. When a candidate surfaces, check it against the question's qualifiers (prospective vs retrospective, who said it, which object) and spend one search looking for a competing candidate before committing — if two values compete, expand both and pick the one whose turn actually matches the question.

**Coverage before counting or ordering.** `ms.sql_query` returns at most 1000 rows and appends a `_truncated` marker beyond that; a `LIMIT` you added yourself truncates the same way, silently. Never aggregate, order, or summarize over a truncated result as if it were complete — chunk by seq/date range (`WHERE seq BETWEEN …`) until the pieces cover the whole span, and verify counts add up.
