# SCROLL — Session-as-Context, Recoverable Off-context LLM Log

*Long-form architecture doc, last revised 2026-05-22. The short-form design rationale lives at [`docs/scroll.md`](../docs/scroll.md); this document expands on it and walks the codebase in roughly the order it executes.*

## 1. Motivation

Long-horizon LLM agents — those running for hours, days, or thousands of turns — fail in three compounding ways when memory and context are conflated:

| Failure | What happens | What SCROLL does |
|---|---|---|
| **Context overflow** | History grows without bound; truncation / summarization silently drops information the agent will later need. | Memory lives outside the model context as an append-only log `E` plus a derived memoryspace `W`. The context itself stays bounded. |
| **Memory–data drift** | Summarized memory references data that has since changed; the agent *thinks* it remembers but reasons against stale facts. | `W = build(E)` is recomputable from the log. There is one source of truth; the memoryspace is a structured view of it. |
| **Blind retrieval** | Without structure, the agent must scan raw history; with bolted-on retrieval, it must guess which tool to use. | Retrieval is **code**. The agent writes Python with `log` and `ms` already bound in a sandboxed REPL; what comes back into the context is whatever the agent's program produces. |

SCROLL ("Session-as-Context: Recoverable Off-context LLM Log") is the reference framework for this pattern, evaluated on three benchmarks: LongMemEval (chat-memory probes), Vending Machine (long-horizon planning), and BEAM (100K–10M-token chat memory).

## 2. The SCROLL Pattern

### 2.1 (E, W, CodeAct) decomposition

Three primitives, separable by responsibility:

```
                    LLM context (bounded)
                            │
                            │ retrieval via Python
                            ▼
              ┌──────── CodeAct REPL ─────────┐
              │  bound globals: log, ms,      │
              │  sub_llm, rlm, env tools      │
              └──────────────┬────────────────┘
                             │ read / query
                ┌────────────┴────────────┐
                ▼                         ▼
        ┌───────────────┐         ┌─────────────────┐
        │  E (the log)  │         │  W = build(E)   │
        │  append-only  │  build  │   memoryspace     │
        │   JSONL of    │ ──────► │  SQL + JSON +   │
        │  every event  │         │ vectors + files │
        └───────────────┘         └─────────────────┘
```

- **E (the log)** — `ConversationLog`. An append-only JSONL where every observation, action, tool call, and LLM message lands with `session_idx` + `turn_idx`. Implementation: [`src/Scroll/log.py`](../src/Scroll/log.py).
- **W (the memoryspace)** — `Memoryspace`. A structured, queryable view derived from `E`: a SQLite database, a JSON document store, a vector index, and a file store. Schema is env-specific (the agent declares it via `_ensure_schema`). Implementation: [`src/Scroll/tools/memoryspace.py`](../src/Scroll/tools/memoryspace.py).
- **CodeAct retrieval** — The agent writes Python in a sandboxed REPL where `log` and `ms` are already bound. Each tool call is one Python snippet; the snippet's stdout becomes the next turn's tool result. Implementation: [`src/Scroll/core/_codeact_agent.py`](../src/Scroll/core/_codeact_agent.py).

`build(E)` is deterministic: identical logs yield identical memoryspaces. This is what makes runs replayable.

### 2.2 Why this isn't just RAG

| Property | Vanilla RAG | SCROLL |
|---|---|---|
| Retrieval interface | One or more named tools (`vector_search`, `sql_query`) | A Python REPL. The agent **composes** retrieval programs. |
| Data model | A vector index (or a few fixed indexes) | SQL + JSON + vectors + files, all queryable in one snippet. |
| Per-turn context | Top-K chunks from a similarity search | Whatever the agent's program prints to stdout. |
| Ingestion | Offline embedder over a static corpus | Online, per-session, env-specific (`_ingest_context` / `_ingest_outcomes` hooks). |

The agent decides what to retrieve **and how to combine it** every turn. It can join a SQL result with a vector hit, run an LLM-side filter via `sub_llm`, or recurse into a sub-agent via `rlm`. The substrate doesn't pick the retrieval strategy; the model does, in Python.

## 3. Task / Session / Turn

Three nesting levels are named consistently throughout the codebase:

| Level | Definition | LongMemEval | Vending | BEAM |
|---|---|---|---|---|
| **Task** | One Scroll run (one `run_single` invocation). | One QA item. | One simulation. | One chat. |
| **Session** | A coherent context chunk inside a task. Marked with `session_idx` in `LogEntry`. | One past chat session being delivered. | One calendar day. | One chat batch. |
| **Turn** | One LLM message inside a session. Marked with `turn_idx`. Each CodeAct loop iteration is one turn. | (1 LLM call per turn) | (same) | (same) |

The agent config knob **`max_iters_per_turn`** caps the CodeAct loop **inside one session** — i.e., how many turns the agent may take to process one session before the framework forces it to commit and move on.

*Vending footnote.* Vending's own SQL schema keeps a `day` column as a domain concept (it's calendar-day-shaped). Inside `VendingAgent`, `day = session_idx` is mapped 1:1; the framework calls it a session, vending's SQL calls it a day. Same value, different vocabulary by layer.

## 4. The Agent Class Hierarchy

```
BaseAgent (abc)
  └── CodeActAgent           generic LLM-loop + REPL substrate
        └── ScrollAgent      adds memoryspace lifecycle + log binding
              ├── LongMemEvalAgent     readonly_memoryspace=True, expose_rlm=True
              ├── VendingAgent          expose_sub_llm=True (writable W)
              └── BeamAgent             readonly_memoryspace=True, expose_rlm=True
```

What each layer does:

| Layer | Concept | Adds |
|---|---|---|
| `BaseAgent` | Agent ABC | `run_session(env)`, `receive_context`, `receive_outcomes`, checkpoint hooks. |
| `CodeActAgent` | "Talks to an LLM, runs Python in a sandboxed REPL." | LLM call loop, REPL runtime, history management, memory modes (`step` / `sliding`), probe-mode machinery. Knows nothing about `W`. |
| `ScrollAgent` | "CodeAct + `W = build(E)`." | Owns `self.memoryspace`. Binds `log` (LogHandle over E) and `ms` (Memoryspace) into the REPL on every session start. Routes `receive_context` / `receive_outcomes` through `_ingest_context` / `_ingest_outcomes` so `W` stays in sync with `E`. |
| `<Env>Agent` | Concrete agent for one env. | Implements the three SCROLL hooks and supplies the prompt strings. |

Why both `CodeActAgent` and `ScrollAgent`? The split exists for paper-narrative reasons: `SCROLL = CodeAct + W`. The `CodeActAgent` layer leaves room for a future log-only baseline (no memoryspace) that would inherit at that level. In the current code there is no such baseline; every concrete agent inherits `ScrollAgent`.

### 4.1 The three SCROLL hooks

Each env subclass must provide:

```python
class MyEnvAgent(ScrollAgent):
    def _ensure_schema(self, memoryspace: Memoryspace) -> None:
        # CREATE TABLE / CREATE VIEW / CREATE INDEX statements that
        # define the env's view of W. Called once at __init__.
        ...

    def _ingest_context(self, session_idx: int, notes: list[str]) -> None:
        # Called when the env hands the agent the new session's content.
        # Write into ms.sqlite / ms.vectors / ms.json_store.
        ...

    def _ingest_outcomes(self, session_idx: int, logs: list[str]) -> None:
        # End-of-session outcome lines (e.g. sales for vending).
        # Optional — leave as no-op for pure-retrieval envs.
        ...
```

Plus the standard `CodeActAgent` overrides for prompt text: `session_prompt`, `sys_prompt`, `namespace_docs`, `extra_namespace`, `_base_namespace`.

### 4.2 Harness toggles

Class-level booleans on `ScrollAgent` / `CodeActAgent` subclasses:

| Flag | Default | What it does |
|---|---|---|
| `readonly_memoryspace` | `False` | Wrap `ms` with a proxy that raises on mutators. Used when the harness owns ingestion (LME, BEAM). |
| `expose_sub_llm` | `False` | Bind a stateless one-shot LM as `sub_llm` in the REPL. |
| `expose_rlm` | `False` | Bind `rlm` (`dspy.RLM`) in the REPL — a recursive sub-agent the model can spawn for sub-questions. Requires `dspy` extra. |
| `memory_mode` | `"step"` | `step` (wipe history at each session boundary) or `sliding` (compress when over budget). |
| `clear_namespace_each_session` | `True` | Wipe REPL globals at each session boundary; persistent state must live in `W`. |

## 5. The CodeAct Loop

Inside one session, the agent runs a bounded loop. Each iteration is one **turn** — one LLM call, possibly followed by one Python execution. The loop ends when either:

- the agent emits a final answer (content without a tool call, or an explicit `wait_for_next_session()` call), or
- the loop hits `max_iters_per_turn` and the framework forces it to commit.

```
session start
  │ → fresh REPL namespace (log, ms, sub_llm, rlm bound)
  │ → optional history wipe (memory_mode = "step")
  │
  ▼
  for it in range(max_iters_per_turn):     # one iteration = one turn
      ┌──────────────────────────────────────────┐
      │ LLM call:                                │
      │   sys_prompt + session_prompt +          │
      │   history (truncated by memory_mode) +   │
      │   namespace_docs                         │
      └───────────────┬──────────────────────────┘
                      │
            either: tool_call (Python snippet)
              └─→ execute in REPL, stdout → next turn's tool_result
            or:    content (the final answer / commit)
              └─→ session ends
```

### 5.1 Either-or turn shape

Each turn produces either a `tool_call` OR a `content` field — never both. This is enforced in the system prompt and in the message-formatting pipeline. The rationale: when both are emitted, the model's "reasoning prose" leaks into the persisted log, making future turn prompts longer and noisier. A clean either-or contract keeps each turn cheap.

For reasoning models with native CoT (qwen3-family with `enable_thinking=true`), reasoning lives in the on-message `reasoning` field; the visible `content` is still either a tool_call OR a final commit, never narrative. SCROLL's default config has `enable_thinking=false` — the agent should externalize its reasoning into code, not into thinking tokens.

### 5.2 REPL namespace

Bound into every snippet:

| Name | Type | Purpose |
|---|---|---|
| `log` | `LogHandle` | Read API over `ConversationLog` (E). Methods: `slice(session=...)`, `range_by_session(start, end)`, `semantic_search(q, k=...)`. |
| `ms` (= `memoryspace`) | `Memoryspace` or `_ReadOnlyMemoryspace` | The W layer. `ms.sql_exec(...)`, `ms.json_read(...)`, `ms.vector_query(...)`, `ms.file_read(...)`, `ms.schema_inspect()`. |
| `sub_llm` | callable (if `expose_sub_llm=True`) | One-shot LM call. Used for in-snippet judgment / extraction. |
| `rlm` | callable (if `expose_rlm=True`) | Recursive sub-agent via `dspy.RLM`. Used for hard sub-questions. |
| env tools | env-specific | Vending exposes `send_email`, `read_email`, `get_money_balance`, `wait_for_next_session()`, etc.; LME and BEAM are read-only. |

### 5.3 Memory modes

| Mode | When applied | Notes |
|---|---|---|
| `step` | All SCROLL agents (default) | Wipes history to `[system, user]` at every session boundary. Cross-session memory lives in `W` and `E`. No auto-compaction within a session. |
| `sliding` | Reserved for baselines | Runs `_compress_history_to_budget` before every model call; folds old turns into `_compressed_summary` once total chars exceed `context_max_tokens * 4`. |

Within a session, `step` mode has **no auto-compaction**: the history grows linearly up to `max_iters_per_turn` turns. The ~4 KB stdout cap per tool result bounds each turn's contribution.

## 6. Benchmarks

Three reference envs ship under `src/Scroll/benchmarks/<env>/`. Each is a self-contained subpackage exporting `ENV_ID`, `ENV_CLS`, `DATASOURCE_CLS`, `parse_env_config`, `create_agent`, and a `tasks` submodule with `PROBES` + `get_probes_for_session`.

### 6.1 LongMemEval — chat-memory probes

| | |
|---|---|
| Upstream | [`xiaowu0162/LongMemEval`](https://github.com/xiaowu0162/LongMemEval) (Wu et al., NAACL 2025) |
| Task structure | One QA item = one Scroll run. N past chat sessions delivered one per `session_idx`, then a single probe on session N+1. |
| Splits | `oracle` (1–6 sessions / <2K toks / 500 items), `s_cleaned` (~50 sessions / ~115K toks / 500 items), `m_cleaned` (~500 sessions / ~1.5M toks / 500 items). |
| Scoring | LLM-as-judge (per-qtype templates from upstream `evaluate_qa.py`); binary 1.0 / 0.0. Canonical judge `qwen3.7-max` (CN Dashscope). |
| Question types | single-session-user/assistant/preference, multi-session, temporal-reasoning, knowledge-update, abstention. |
| Agent class | `LongMemEvalAgent` (`readonly_memoryspace=True`, `expose_rlm=True`). |

LME is the "pure retrieval" point: the harness owns ingestion (writes chat turns into `W`), the agent's job is to read. The agent's prompt is dominated by the probe question and the memoryspace schema.

### 6.2 Vending Machine — long-horizon planning

| | |
|---|---|
| Task structure | One Scroll run = one 30–180-day vending sim. Each session is one calendar day. |
| Mechanics | Agent manages 12 machine slots / 6 max SKUs, sets prices, orders from suppliers (3-day lead), pays $2/day operating fee. Demand model is seeded (price elasticity × weekday × season × noise). Bankruptcy at 10 consecutive negative-cash days. |
| Probes | 29 scheduled mid-task probes at days 10–180 — 16 factual recall (Cat A: "total revenue days 6–9"), 13 analytical (Cat B: "top cumulative-profit SKU"). |
| Scoring | Deterministic — numeric (5% tolerance) or keyword overlap. |
| Agent class | `VendingAgent` (`expose_sub_llm=True`, writable memoryspace). |

Vending is the only env where memory quality has a direct $ signal: a probe answered wrong is a missed business decision. The agent owns its memoryspace and writes its own ingest passes.

### 6.3 BEAM — long-context chat memory

| | |
|---|---|
| Upstream | [`mohammadtavakoli78/BEAM`](https://github.com/mohammadtavakoli78/BEAM) (Tavakoli et al., ICLR 2026, [arXiv:2510.27246](https://arxiv.org/abs/2510.27246)) |
| Task structure | One Scroll run = one chat. Sessions are batches of the chat (3–24 batches per chat depending on scale). Probes fire on the final session. |
| Scales | 100K, 500K, 1M, 10M tokens per chat. |
| Probes | 20 questions per chat, each tagged with one of 10 ability categories: information_extraction, multi_session_reasoning, knowledge_update, temporal_reasoning, abstention, contradiction_resolution, event_ordering, instruction_following, preference_following, summarization. |
| Scoring | Per-rubric-item LLM judge (`gpt-4o-2024-08-06` canonical). |
| Agent class | `BeamAgent` (`readonly_memoryspace=True`, `expose_rlm=True`). |

BEAM is the scale stress test: memoryspaces hold up to 10M tokens of chat history, and the probes require the agent to recover specific facts, reconcile contradictions, and order events across that horizon.

## 7. Evaluation

### 7.1 Probe lifecycle

```
session N completes
   │
   ▼
get_probes_for_session(N) → list[ProbeSpec]    # env-specific schedule
   │
   ▼
for probe in probes:
    inject_probe(agent, probe, snapshots, data)
       │
       ▼
    swap agent into probe mode:
      - new sys_prompt (probe-specific)
      - wait_for_next_session() becomes a no-op
      - max_iters_per_turn cap stays
    agent.run_session(env)  ← agent answers
    score = probe.scorer(agent_answer, ground_truth)
    write ProbeResult
   │
   ▼
restore agent to session-loop mode
```

`ProbeSpec` carries the question, the scorer, the ground-truth slot, and `session_idx` (when to fire). For envs with end-of-task probes (LME, BEAM), all probes fire on session `num_sessions + 1`. For Vending, probes are scheduled mid-task.

### 7.2 LLM judge

Both LME and BEAM judges run through the OpenAI client at the configured `judge_api_base`. The `enable_thinking=False` extra is gated on Dashscope endpoints (it's a qwen-only knob; the OpenAI endpoint rejects unrecognized args with HTTP 400).

### 7.3 L3 distillation (LME only)

When `enable_distillation=True`, after each LME probe completes, a sub-LM call distills the probe's trajectory into a **case-study hint** that gets persisted in `_shared_memoryspace.json`'s `procedural_hints` table. The hint has:

- `qtype` — which question type it generalizes (e.g. `temporal-reasoning`).
- `pattern` — a short slug identifying the retrieval pattern used.
- `summary` — one-sentence guidance for future probes of the same shape.

When `enable_playbook=True`, the distilled hints are spliced into the next probe's prompt under a `DISTILLED PLAYBOOK` block. The harness can run with playbook on (read curated guidance) and distillation off (don't pollute the store with weaker-model hints) or vice versa — useful for cross-model transfer experiments.

## 8. Memoryspace (the W layer)

`Memoryspace` exposes four data shapes through one Python object:

```python
ms.sqlite                      # raw sqlite3.Connection
ms.sql_exec(stmt, params)      # → list[dict]
ms.json_read(key)              # → any
ms.json_write(key, value)
ms.json_list()                 # → list[str]
ms.vector_query(q, top_k=5)    # → list[(score, key, text)]
ms.vectors.add(key, text)
ms.file_read(name)             # → str
ms.file_write(name, content)
ms.file_list()                 # → list[str]
ms.schema_inspect()            # → CREATE TABLE statements + row counts
```

### 8.1 Read-only proxy

LME and BEAM wrap `ms` in `_ReadOnlyMemoryspace`: every mutator raises `PermissionError`, but reads pass through. This enforces the "harness writes, agent reads" contract for pure-retrieval envs. Scratch state lives in Python locals (cleared at the session boundary).

### 8.2 Ingestion

Three patterns across the three envs:

| Env | Ingestion |
|---|---|
| LongMemEval | Harness-owned. `LongMemEvalAgent._ingest_context` writes the new session's chat turns into `chat_turns`, indexes them in the vector store, and updates a `session_summary` row. The agent never writes. |
| BEAM | Harness-owned. `BeamAgent._ingest_context` does the same shape as LME — writes chat turns, extracts polarity / facts / dates into auxiliary tables, indexes turns and per-session summaries. |
| Vending | Agent-owned (writable). `VendingAgent._ingest_context` and `_ingest_outcomes` populate email inbox, supplier prices, sales, deliveries, finances, inventory. The writes are defined by the agent code, not by code the LLM emits. |

## 9. Checkpoint / Resume

Long-horizon runs (Vending 180-day, BEAM 10M-token) span hours and thousands of LLM calls; any rate-limit, timeout, or transient error would otherwise mean restarting from scratch. After every session, `_run_session_loop` writes:

```
output/<env>/<policy>_<seed>_<config-hash8>/
└── checkpoints/
    ├── session_001/
    │   ├── agent_state.json        # CodeActAgent: history, iter counters, namespace
    │   ├── memoryspace.json          # SQL dump + JSON store + vector entries + files
    │   ├── env_state.json          # env-specific: sim state, RNG, datasource state
    │   ├── loop_state.json         # snapshots, message budget, probe results so far
    │   └── _meta.json              # version, timestamp, session_idx, config hash
    ├── session_002/
    │   ...
    └── latest → session_NNN/       # symlink to most recent
```

On startup, `run_single()` checks `checkpoints/latest`. If `_meta.json` matches the current `(strategy, seed, config_hash)`, the run resumes from `session_idx + 1`; otherwise it aborts with a config-mismatch error. `--fresh` ignores existing checkpoints; `--no-checkpoint` disables writes for ephemeral runs.

A fresh `Agent` is created at each session boundary and immediately calls `from_checkpoint(...)`. This makes "normal session transition" and "crash recovery" the same code path. RNG state is round-tripped so resumed runs are bit-identical to uninterrupted ones.

## 10. Tracing

Optional OTLP tracing via `--tracing-url`. Spans flow into Phoenix or any compatible backend.

```
Scroll.run (root)
└── session.{N}
    ├── agent.run_session
    │   ├── llm_call.{turn}     ← one per CodeAct iter
    │   ├── code_exec.{turn}    ← one per snippet
    │   └── sub_llm / rlm       ← when invoked
    ├── env.step_session
    └── probe.{question_id}     ← if scheduled
        └── judge.{category}    ← LLM-judge call
```

Key span attributes:

| Span | Attributes |
|---|---|
| `Scroll.run` | `run.strategy`, `run.seed`, `run.config_hash`, `run.net_worth`, `run.units_sold`, `run.active_sessions`, `run.avg_probe_score` |
| `session.{N}` | `session.idx`, `session.turn_count`, `session.message_budget_remaining` |
| `llm_call.{turn}` | `llm.model`, `llm.input_tokens`, `llm.output_tokens`, `llm.tool_call.name`, `llm.content_chars` |
| `code_exec.{turn}` | `cell.session`, `cell.iter`, `code.lines`, `code.stdout_chars`, `code.exception` |
| `probe.{id}` | `probe.question_id`, `probe.category`, `probe.score`, `probe.agent_answer`, `probe.ground_truth` |
| `judge.{category}` | `judge.model`, `judge.verdict`, `judge.score` |

Phoenix UI: `docker run -p 6006:6006 arizephoenix/phoenix:latest`, then pass `--tracing-url http://localhost:6006/v1/traces` to the `Scroll` CLI.

## 12. What's intentionally NOT here

- **Baselines.** Every non-SCROLL agent was removed in the consolidation pass (basic, code_agent, agentscope_reme, rlm-only, database_*, adaptive*). Re-adding one for paper comparison is a future task: it would inherit from `CodeActAgent` (skipping the `ScrollAgent` memoryspace layer) to give a clean "log-only" or "RAG-only" point on the design spectrum.
- **MemoryBench.** Scoped in but never wired up — left out of v1 to keep the benchmark set focused on memory-read tasks. Memory-**write**-under-feedback is a separate axis.
- **Two-stage planner+actor loop.** The old DataForce design (planner with out-of-band data tools + actor with action tools) was retired when CodeAct landed. The model now picks retrieval composition directly in the same loop as side-effect actions; there is no separate "context planner" call.
