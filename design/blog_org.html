The Python REPL is the Memory API

CodeAct for Memory Management & Scripts as Procedural Memory

CodeMe gives long-horizon agents a set of storage primitives — SQL, vectors, files, JSON — and at each turn the agent writes Python to decide which surface to query, in what combination, with what filters. The full LongMemEval-S (500 QAs, ~115K tokens each) runs for $9.6 at 87.6% accuracy; the full LongMemEval-M (500 QAs, ~1.5M tokens each) for $12.6 at 77.6% with Qwen3.6-plus. The cost stays low because the model never reads the haystack — ingest-time structured storage compresses sessions into an index, so the LLM programmatically examines only the relevant slices of the long-term history: ~3.7 CodeAct reasoning steps and 40.8K prompt tokens per QA.

tl;dr

Every modern memory system — Mem0, Zep, Hindsight, Supermemory, Mastra OM — settles on one retrieval pipeline at build time and ships it. CodeMe does the opposite: keep the storage primitives (SQL, vectors, files, JSON), but let the agent write Python at every turn to decide which surface to query, in what order, with what filters. The retrieval pipeline is whatever the agent writes today. On LongMemEval-S (500 QAs, ~115K tokens each) CodeMe scored 0.874 with qwen3.6-plus; on LongMemEval-M (~1.5M tokens) 0.776, where most published systems don't report at all — the leaderboard leader at S (Mastra OM at 94.87%) is a context-only approach that compresses the conversation into a stable prompt, which doesn't scale to 1.5M-token haystacks. CodeMe works on both splits because the agent never reads the full haystack, just indexed query results. Cost: ~3.4 LM calls and ~40.8K prompt tokens per QA — driven by what the architecture asks of the model, not by model size.

Where we sit

LLM coding and orchestration ability is improving rapidly. A fixed retrieval pipeline captures one point in that curve — to do better, someone has to redesign it. CodeMe's retrieval logic is whatever Python the agent writes today: as models get better at composing SQL, vector queries, and sub-LLM calls, so does the retrieval, without touching the architecture.

The dimension along which we differ from every system in the table above is who writes the retrieval code.

Most systems above fix the retrieval pipeline at build time. ReMe and MemGPT/Letta let the LLM decide when and how often to call retrieval tools — but the tools themselves are still a fixed API the designer chose in advance.

In CodeMe, the agent's interface to memory is Python. It has retrieval primitives:

  • memoryspace.sql_exec(stmt, params) — read-write SQL against an in-memory SQLite.
  • memoryspace.vector_query(q, top_k) / vector_store_add(key, text) — bag-of-words vector store.
  • memoryspace.json_write(key, data) / json_read(key) — nested-dict storage.
  • memoryspace.file_write(name, content) / file_read(name) — raw text blobs.
  • log.slice(day, kind) / log.semantic_search(q) / log.findall(regex) — read-only views of the unified event log E.
  • await rlm(prompt) — the RLM primitive for delegating sub-tasks (extraction, ranking, generation) from within a code cell, without re-passing the full context.

At each turn — both during ingest and at probe time — the agent decides which of these to use, in what combination, with what filters. There's no fixed pipeline. A retrieval cell at probe time might look like:

sql_hits  = memoryspace.sql_exec(
    "SELECT day, content FROM chat_turns WHERE content LIKE ?",
    params=(f"%{keyword}%",))
vec_hits  = memoryspace.vector_query(question_paraphrase, top_k=8)
log_hits  = log.semantic_search(question, kind="chat_turn", k=10)
candidates = merge_dedup(sql_hits, vec_hits, log_hits)
ranked = await rlm(f"Rank by relevance to {question}:\n{candidates}")

Or it might just be a single SELECT from a denormalized observations table. Or a regex over the raw log. The agent picks per probe, and on the same QA on a different day it may pick differently.

This isn't conceptually new — it's just CodeAct (Wang et al.) applied to memory operations instead of tool calls. Existing memory systems generally don't take the CodeAct interface seriously because they treat memory as an external service. We treat it as a Python REPL with a SQL connection.

An analogy: existing memory systems give the agent a notes app with a GUI. CodeMe gives the agent a shell and a database. The latter demands a stronger agent — but the ceiling is much higher.

This design generalizes cleanly. The ingest layer is framework-agnostic: it reads from the conversation log E, which any agent framework produces. The memory primitives — SQL tables, vector index, JSON store — are a pluggable component; nothing in the storage layer is specific to any orchestration framework. The one requirement on the agent side is a CodeAct substrate: the agent needs to be able to execute Python. Any agent that can run a REPL can use CodeMe's memory primitives without modification.

Procedural memory: distilling lessons across runs

One direction we explored is whether CodeMe can accumulate knowledge across QAs — not just within a single run, but as transferable procedural memory. After each probe, a sub-LLM distills the successful trajectory into a structured lesson:

{
  "qtype": "multi-session",
  "polarity": "success",
  "pattern": "information_extraction",
  "trigger": "question requires counting distinct entities matching multiple semantic criteria across sessions",
  "lesson": "Use broad keyword SQL filters to gather candidates, then delegate counting and deduplication to rlm — SQL alone cannot reliably resolve semantic nuance like 'heirloom' vs 'gift'.",
  "code": "rows = ws.sql_exec(\"SELECT session_idx, turn_idx, content FROM chat_turns WHERE role='user' AND (content LIKE '%antique%' OR content LIKE '%vintage%' OR content LIKE '%heirloom%') ORDER BY session_idx, turn_idx\")"
}

We tested two ways to transfer these lessons to weaker models:

  • Playbook — synthesize all accumulated lessons into a structured 14K-char skill document, appended to the probe prompt. The strong model's patterns become a written guide.
  • Top-K hints — at probe time, inject the top-K lessons from the shared store that match the current question type, filtered by polarity and source QA. The model sees concrete SQL templates, not abstractions.

But the gains are modest: the base prompt quality and the model's own coding ability remain the primary bottleneck. Procedural memory can transfer patterns, not capability.

Where it still breaks

Looking at the 64 failures out of 500 on qwen3.6-max-preview S (qwen3.6-plus tracks the same pattern at 63 failures): multi-session is 29 of those, temporal-reasoning and knowledge-update 15 each — single-session is a long-solved tail at ≤3 misses per qtype. But the qtype breakdown is the wrong axis to look at. Read the actual failures and a much sharper pattern emerges: in nearly every miss, the agent already retrieved the right row. The error is downstream of retrieval.

The retrieval is not the bottleneck

None of the five misses above are recall failures. The popular memory-system upgrades — hybrid retrieval (vector + BM25 fusion with weighted scoring), cross-memory entity linking, time-aware ranking — are all retrieval-side improvements. They make top-K better. But our 64 failures don't sit in top-K mistakes; they sit in what the agent does after retrieval lands the right candidate. A better fusion score wouldn't change the answer on any of the five cases above.

This is the core architectural argument for CodeMe. The agent doesn't issue a query and read top-K; the agent writes Python. So the leverage point isn't "how do I rank candidates better" — it's "how do I get the agent to write better procedural code." Three patterns would close most of the remaining gap:

  1. Intent-branch on the question first. "How many years older / how long have I" matches a derivation pattern: find two anchor dates, subtract. Don't search for the answer as a string when the answer doesn't exist as a string.
  2. Anchor-and-sweep instead of stop-at-first-hit. When the question is "current X" and the first explicit mention is from session 1, the agent must scan every later session for any entity-related mention — periphrastic update phrasing ("grew the team to 5", "now have 5 reports") rarely repeats the original sentence shape.
  3. Switch to sub-LM read when SQL keyword search converges on nothing or on a window. The current code stays in SQL too long. After 2 dry SQL queries, or after retrieving a date-anchored window of 5+ turns, hand the rows to rlm and read the natural language — cheaper than a third SQL retry and structurally more likely to find the answer.

The same observation gives a structural lever too: at ingest time, run a sub-LM extractor that builds a user_state_timeline table of (entity, attribute, value, session_idx, date, polarity) tuples. Then "current role tenure" or "engineers led now" becomes a single ORDER BY DESC LIMIT 1; the procedural patterns above are absorbed into the schema rather than relied on to emerge from the agent each time. Shifting work from agent-runtime to ingest-time is the cleaner play once a query pattern is well-understood.

The retrieval-side upgrades — Mem0-style fusion, entity boost, temporal rank — aren't wrong, they're orthogonal. They help systems whose bottleneck is a single round-trip query against a fixed index. CodeMe's bottleneck is the agent's choice of procedure, and you can't fuse your way out of a procedure problem. The fix is either better code (prompt-level intent rules, sub-LM read defaults) or a substrate that pre-computes the joins the agent would otherwise have to write — either way, the leverage sits above retrieval, not inside it.

Why writing Python beats calling tools

The benchmark numbers above are the existence proof. The deeper question is why a CodeAct interface to memory beats a fixed tool API. Seven technical reasons.

1. Composition is free

Give an agent a search(query, filter) API and it can only call that one thing. Give it two APIs and it can chain them. Give it Python, and it can write:

sql_hits = memoryspace.sql_exec("SELECT ... WHERE day BETWEEN ? AND ?", (d1, d2))
keywords = await rlm(f"extract keywords from: {question}")
vec_results = []
for kw in keywords:
    vec_results.extend(memoryspace.vector_query(kw, top_k=5))
merged = {h['key']: h for h in sql_hits + vec_results}.values()
filtered = [h for h in merged if h['score'] > 0.6]
ranked = sorted(filtered, key=lambda h: (h['day'], -h['score']))[:10]

Control flow, data structures, variable binding, multi-stage reasoning — all free. To express the same thing as tool calls you'd either design an explosively-parameterized search API or fire ten separate tool calls and burn LLM context on each round-trip. Adding a primitive doesn't add 1 strategy, it multiplies the number of expressible strategies by N.

2. Intermediate state stays in the execution environment

Every tool call result has to fly back to the LLM — agent reads it, decides next step, calls next tool. Every intermediate value lives in the prompt. CodeAct doesn't:

candidates = expensive_retrieval()  # 200 rows
top = rerank(candidates)[:10]       # cut to 10 in Python
return top

Those 200 rows never enter the LLM's context. Only the final 10 do. For memory operations this matters more than usual: SQL queries can return thousands of rows, vector retrieval surfaces low-score noise. CodeAct lets you filter in Python so the LLM sees the signal, not the noise. This is the primary reason 40.8K prompt tokens per QA is so low.

3. Conditional execution is natural

Many memory operations are conditional: "if SQL gave me enough, don't bother with vector."

sql_hits = memoryspace.sql_exec("...")
if len(sql_hits) >= 5:
    return sql_hits[:5]
else:
    vec_hits = memoryspace.vector_query(question)
    return merge(sql_hits, vec_hits)

Expressing this with tool calls requires the agent to call a tool, read the result, then decide whether to call the next — one LLM round-trip per branch. In CodeAct, short-circuit logic is free.

4. Type differences become an implicit contract

Writing SQL commits to "structured data with a schema." Writing a vector query commits to "fuzzy match, no precision guarantee." Writing json_read commits to "exact key lookup." These distinctions are invisible at the tool API level — all tools look like tool(input) → output. In Python, the agent is forced to think about which kind of access it wants. This is what makes the memoryspace's tiered storage (BoW vs SQL vs JSON) actually work — the agent has to commit to a type of access when it writes the code.

5. Failures can be caught and handled

try:
    result = memoryspace.sql_exec("SELECT ... WHERE day = ?", (target_day,))
    if not result:
        result = memoryspace.vector_query(question, top_k=10)
except SQLError:
    result = log.findall(question)

Tool-call frameworks can do exception handling but it's awkward. In Python it's native. Long-horizon agents need this — memory operations fail (missing keys, schema drift, query errors) and the agent has to recover gracefully.

6. Readable, debuggable, auditable

The agent's reasoning is the code itself. When QA #47 fails, you can look at the Python cell the agent wrote, see what it tried, and fix a system prompt to nudge it differently next time. With tool calls, the "decision" is buried in the LLM's implicit reasoning and you debug by reading thinking traces. CodeAct turns reasoning into an artifact engineers can read and modify.

7. Rides the model capability curve

Writing code is one of the fastest-improving LLM capabilities — every model generation moves further on coding than on instruction following or general reasoning. Binding the memory interface to "the agent writes code" means the system rides this curve automatically: architecture stays the same, model gets better, retrieval gets better. Tool-calling capability saturated a long time ago; there's no curve to ride.

What this means for memory systems

"Agentic memory" today mostly means "an LLM decides what to store and delete behind a fixed API". On this benchmark the honest version of that label is something stronger: the LLM writes the storage and retrieval code itself, including, optionally, the schema. Anything weaker is a more flexible Mem0 — useful, but not exercising what the model can actually do.

None of this rules out vector stores, graphs, or rerankers. CodeMe uses SQL, vectors, files, and JSON. The change is that the agent decides when to call each, in what order, with what filters — not the system designer.

A useful frame for evaluating the long-term durability of any memory system: what is it betting the LLM can't do? MemGPT bet that LLMs couldn't handle tool-call loop control and context paging — that capability shipped in the next model generation, and the abstraction became unnecessary. Systems built around external data structures (Mem0's hybrid index, Zep's knowledge graph, Hindsight's four-network store) are more robust: those abstractions don't live on the LLM vendor's roadmap. Mastra OM bets on prompt caching costs staying low enough to make full-context compression viable at scale.

CodeMe's bet runs in the opposite direction: instead of betting on what LLMs can't do, it bets on what they're getting better at — writing code. The structured storage layer (SQL, vectors) is the durable abstraction; the retrieval logic is whatever the model writes today, and it improves as the model does. The only scenario where this breaks down is the Mastra OM end-state: infinite context at negligible cost. The M-split numbers suggest that end-state is still far enough away that an indexed retrieval layer remains worthwhile.

1. Naive Vector RAG

Embed the question, take cosine top-k against per-turn embeddings.

top-5 by similarity:
  Session 12 (0.78)  — "Lisa's birthday"
  Session 18 (0.72)  — "Lisa, Higashiyama Kaii"
  Session 47 (0.69)  — "Lisa likes the art book"
  Session 25 (0.65)  — "where to buy art books"
  Session 03 (0.58)  — unrelated mention of Lisa

Session 31 — the only session containing the answer — ranks 8th. "Ordered" and "Tōshōdai-ji" don't embed close to "bought" and "art book". The reader model sees five passages, none of which contain the title. Fails.

2. BM25

Inverted index on tokens. Query tokens: {Lisa, art, book, bought}.

Sessions containing "art book": 25, 47. Sessions containing "bought": none (the relevant turn uses "ordered"). Session 31 doesn't surface — lexical mismatch. Fails.

3. Mem0 (LLM-extracted fact list)

At ingest, an LLM reads each turn and extracts atomic facts; duplicates are merged, contradictions trigger updates. Storage is a flat list of natural-language fact strings, each with an embedding. For our scenario the ingest pipeline might produce:

fact_001: "User's wife is Lisa"                          [from S12]
fact_002: "Lisa learned watercolor"                      [from S18]
fact_003: "Lisa likes Japanese painter Higashiyama Kaii" [from S18]
fact_004: "User ordered Tōshōdai-ji as birthday gift"    [from S31]
fact_005: "Lisa enjoyed the art book"                    [from S47]

At probe time: vector search over fact embeddings. If fact_004 was extracted with the recipient bound — e.g., "User ordered Tōshōdai-ji as a birthday gift for his wife Lisa" — vector retrieval hits it and answers. If the extractor dropped the recipient (a real failure mode: the turn says "I ordered Tōshōdai-ji as a birthday gift", and "for Lisa" is only implicit from S12), then probing for "art book bought for Lisa" misses, and the flat fact list has no way to compose fact_001 + fact_004 to recover.

Succeeds or fails at ingest, not at probe time. Mem0's strength relative to Naive RAG is exactly this ingest-side LLM extraction: facts are denser and more searchable than raw turns. Its weakness relative to Hindsight or CodeMe is that probe-time reasoning is single-shot vector retrieval over a flat list — no graph traversal, no multi-step composition, no fallback strategy if the first query misses.

4. Zep / Graphiti (knowledge graph)

At ingest, the system extracts a temporal entity-relation graph:

(User) --has_spouse--> (Lisa)
(Lisa) --likes_artist--> (Higashiyama Kaii)  [valid_from: Jan 28]
(User) --purchased--> (Tōshōdai-ji)          [valid_from: Feb 25,
                                              recipient: Lisa,
                                              purpose: birthday_gift]
(Lisa) --enjoyed--> (Tōshōdai-ji)            [valid_from: Apr 20]

At probe time, the LLM translates the question to a graph traversal: User --purchased--> ? WHERE recipient=Lisa. Direct hit on Tōshōdai-ji. Succeeds — if the ingest got the graph right.

The fragility is at ingest. If the extractor reads "I ordered Tōshōdai-ji" without binding recipient=Lisa or purpose=gift, the edge points nowhere useful and the same query fails. Zep's 71.2% on LongMemEval reflects this: graph extraction is a brittle commitment.

5. Hindsight (multi-strategy + rerank)

Four channels in parallel:

  • Semantic: same as Naive RAG. Session 31 mid-rank.
  • BM25: Session 31 low-rank (lexical mismatch).
  • Graph spreading activation: start from Session 47 (top semantic hit), spread along shared entities ("Lisa", "art book"), shared time window (Apr → before), and causal links (purchase → enjoyment). Session 31 lights up brightly.
  • Temporal: "that" parsed as a weak past-time constraint; minor filtering.

RRF combines the four ranked lists. Graph activation pushes Session 31 into the top RRF tier. Cross-encoder reranker (ms-marco-MiniLM) then jointly encodes (question, Session 31) and scores 0.92 — it sees "ordered" ≈ "bought", "Tōshōdai-ji" as a book title. Session 31 ends top-1. Succeeds.

No single channel finds it reliably. The four-way ensemble is the point.

6. Mastra OM (context compression, no retrieval)

Background Observer agents have already compressed all 50 sessions into a stable observation log (~30K tokens):

[obs 12, Jan 15] 🟡 User's wife Lisa's birthday next month
[obs 18, Jan 28] 🟢 Lisa learning watercolor, likes Higashiyama Kaii
[obs 25, Feb 10] 🟢 Recommended several Higashiyama Kaii art books
[obs 31, Feb 25] 🔴 User ordered "Tōshōdai-ji" art book as Lisa's birthday gift
[obs 47, Apr 20] 🟢 Lisa received and enjoyed the art book
...

At probe time the entire log is in the prompt. No retrieval call. The LLM reads everything and answers. Succeeds.

This works because 30K tokens fit and the LLM can reason jointly over all observations. On LongMemEval-M (1.5M tokens → ~250K compressed) the same architecture breaks: the compressed log no longer fits in any model's context window.

7. EmergenceMem (query rewriting + accumulator)

LLM first rewrites the question into multiple variants:

1. "purchase art book gift Lisa"           (keyword form)
2. "user bought book for spouse as gift"   (semantic form)
3. HyDE: "The art book you bought Lisa
   was {X} by Higashiyama Kaii..."         (hypothetical answer)

Each variant runs through vector + BM25. Then an "accumulator" walks sessions sequentially, maintaining running notes. At Session 31 it writes down "Tōshōdai-ji" and carries the note forward. Succeeds.

Closer to CodeMe in spirit (multi-stage, adaptive) but the pipeline is still fixed: same three variants, same accumulator, every probe.

8. CodeMe (CodeAct iterative reasoning)

No fixed pipeline. The agent enters a Thought → Code → Observation loop and decides per-turn what to do next.

Turn 1 — exploratory scan
Thought: User is asking about a past purchase. Let me check the log for mentions of Lisa and art books.
hits = log.findall(keywords=["Lisa", "art book"], window=2)
for h in hits[:5]:
    print(f"Day {h.day}: {h.snippet[:100]}")
Day 18: Lisa has been into watercolor, loves Higashiyama Kaii Day 25: User asks where to buy Higashiyama Kaii art books... Day 47: Lisa really likes the art book
Turn 2 — notice the gap
Thought: I see Day 25 discussing buying and Day 47 referencing "the art book", but no "bought it" record between them. The word "bought" may be missing — let me widen the search semantically.
hits = log.semantic_search(
    "user purchased book album for Lisa as gift",
    top_k=8)
for h in hits:
    print(f"Day {h.day}: {h.snippet[:120]}")
Day 47: Lisa really likes the art book Day 25: User asks where to buy Higashiyama Kaii art books Day 31: I ordered "Tōshōdai-ji" as a birthday gift Day 18: Lisa learning watercolor... Day 12: Lisa's birthday is next month, wants to get her a gift
Turn 3 — lock in the evidence
Thought: Day 31 has "Tōshōdai-ji", "ordered", "birthday gift". Looks like the answer. Let me pull the surrounding context to confirm it's an art book and meant for Lisa.
context = log.slice(day=31, before=2, after=2)
print(context)
[Day 25] User: My wife loves Higashiyama Kaii, can you recommend his art books? [Day 25] Assistant: Tōshōdai-ji, A Single Leaf, The White Horse Forest... [Day 31] User: That Tōshōdai-ji you recommended, I ordered it as a birthday gift. [Day 31] Assistant: Great choice... [Day 47] User: Lisa's birthday last week — she loves the art book.
Turn 4 — answer
Thought: Evidence chain is complete. Day 25 recommends, Day 31 orders Tōshōdai-ji as Lisa's birthday gift, Day 47 confirms receipt.
return "Tōshōdai-ji (by Higashiyama Kaii)"

Succeeds. Four things to notice:

  1. Reasoning is multi-step. Other systems are one-shot: retrieve once, read once, answer. CodeMe interleaves retrieve → observe → judge → retrieve.
  2. Each query is a function of the previous observation. Turn 2's semantic search exists because Turn 1 returned no "bought" record. Hindsight's four-way retrieval is static and runs identically for every probe; CodeMe's query depends on what it just saw.
  3. The agent decides when to stop. After Turn 3 the evidence chain is closed, so the agent answers. If it weren't closed, it would have written Turn 4, Turn 5.
  4. No write-time commitment to a schema for this probe. The retrieval logic is materialized at probe time by Python the agent writes; on a different probe the same agent might write very different code.

The point of this walk-through isn't that CodeMe is the only system that solves this probe — Hindsight and Mastra OM also get it. The point is the shape of how each system gets there. Six of the eight have a single retrieval moment that either works or doesn't. CodeMe is the only one where retrieval is a small program the agent writes for this specific question, on this specific day, with this specific log.

That shape is what scales to the M split. Mastra OM's "read the whole compressed log" stops working when the compressed log itself exceeds 200K tokens. Hindsight's four-way pipeline still works but its noise grows with the haystack — every channel returns more candidates, the reranker has to discriminate harder. CodeMe's loop is invariant to haystack size because the model never reads the haystack — it reads the rows that came back from a query.
